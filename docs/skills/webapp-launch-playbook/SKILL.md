# AI Web 应用上线工作流（Playbook）

> 来源：一个真实项目（Streamlit + 智谱 GLM + PostgreSQL + 飞书机器人 + 阿里云 ECS）从零到 7×24 运行的全过程。
> 用法：新项目开始时，从阶段 0 顺序推进；每阶段结束检查「门禁」，不通过不要进下一阶段。

---

## 全局原则（先读这 6 条）

1. **先跑通最短链路，再谈架构**
   第一版只要「输入 → 处理 → 输出」能走通，别一上来就微服务。
2. **数据源只能有一个**
   两套数据源（如云数据库 + 本地文件）必然不一致，这是最难查的 bug。
3. **密钥永远不进代码**
   `.env` + `.gitignore`，从第一个 commit 就这样做。
4. **生产环境和开发环境必须能重建**
   要么 Docker，要么一份能一键执行的部署脚本。
5. **没有监控 = 没上线**
   服务挂了你不知道，等于没部署。
6. **每一步都留可回滚的出口**
   改表前备份、改代码前 commit、改配置前记下原值。

## 阶段 0 · 需求与边界（30 分钟）

**目标**：明确「给谁用、解决什么、不做什么」。

**动作**
- 写一句话需求：「给 ___ 用的 ___ 系统，解决 ___ 问题」
- 列出 3 个核心功能（超过 5 个就是没想清楚）
- 明确**非目标**（本期不做什么）
- 估算数据量（决定用 SQLite 还是 PostgreSQL）

**产出**：`README.md` 开头三段的草稿

**门禁**
- [ ] 能用一句话说清做什么
- [ ] 知道用户是谁、在哪访问（浏览器/手机/IM）
- [ ] 知道数据量级（< 1万条 → SQLite 够；否则 PostgreSQL）

---

## 阶段 1 · 本地原型（1~2 天）

**目标**：本机能跑，核心链路通。

**动作**
1. 建虚拟环境：`python -m venv .venv`
2. 最小依赖清单，先不装重的（PyTorch/TensorFlow 之类留给第二阶段）
3. 先写「数据流」，再写界面
4. 第一个 commit 就配好 `.gitignore`（含 `.env`、`*.db`、`.venv`）
5. 用 **Streamlit / Gradio** 这类工具快速出界面，别先做前端

**产出**：`app.py` 可运行

**门禁**
- [ ] `python app.py` 能启动
- [ ] 核心链路（输入→处理→输出）走通一次
- [ ] `.env` 已创建、已加入 `.gitignore`、`git status` 里看不到它

**常见坑** → `references/pitfalls.md` 的「Python 环境」「Git」章节

---

## 阶段 2 · 数据层设计（半天）

**目标**：数据结构定下来，且能演进。

**动作**
1. 画表结构：主键、唯一约束、索引
2. **唯一约束是去重的基础**（本项目：`发票号码 UNIQUE` → 重复上传自动更新）
3. 先写 `schema.sql`（可读、可重建），别用 ORM 自动建表
4. 数据量 < 1 万条：SQLite 够用，别上云数据库
5. 需要多端共享/并发写 → PostgreSQL
6. 从一开始就准备 `finance_test` 这类**独立测试库**

**产出**：`schema.sql`（含注释、索引）

**门禁**
- [ ] 表结构能从空库一键重建
- [ ] 关键字段有唯一约束或索引
- [ ] 有独立测试库

**常见坑** → 「数据库」章节（中文列名引号、连接池泄漏、密码含特殊字符）

---

## 阶段 3 · LLM / AI 集成（1~2 天）

**目标**：模型能按需调用工具，而不是只会闲聊。

**动作**
1. 选模型：先用便宜快的（如 GLM-4-Flash），够用就不升级
2. **工具（Function Calling）设计**：
   - 工具名 = 动作（`query_invoice_db`），描述里写清「什么时候用」
   - 参数尽量少，必填项明确
   - 工具返回**结构化文本**（不是 JSON 塞给用户）
3. **系统提示词写死规则**，例如：
   - 「涉及数字的问题必须先调工具，不许编造」
   - 「通用词（发票/总额）不要当公司名去查」
   - 「工具返回空时换更短的关键词重试一次」
4. 常驻进程要处理：**流式失败、超时、重试、去重**
5. 对用户输入和模型输出都做长度限制

**产出**：可用的 Agent 循环（最多 3 轮工具调用）

**门禁**
- [ ] 问「查某公司金额」能真去查库，不是瞎编
- [ ] 问「一共多少条」这类总体问题，走的是统计工具而不是模糊查询
- [ ] 工具报错时，回复是友好提示而不是崩

**常见坑** → 「LLM 集成」章节（通用词当参数、对话历史无限增长、提示词注入）

---

## 阶段 4 · 外部系统集成（1 天）

**目标**：接进用户真实的工作流（IM、审批、邮件）。

**动作**
1. 优先选**长连接**方案（如飞书 WebSocket），不需要公网回调地址、不需要备案
2. 权限最小化：只申请用得到的 scope
3. **改权限必须重新发版本**，不发布不生效
4. 消息去重（`message_id` 缓存），IM 会重投
5. 群里 @ 机器人时，正文里会带 `@_user_1` 这类占位符，要清掉

**产出**：`bot_server.py`（或等价集成服务）

**门禁**
- [ ] 外部系统发消息，服务能收到并回
- [ ] 服务重启后能自动重连
- [ ] 断网恢复后能自愈（项目里实测过：欠费 20 分钟断线 14 次后自动恢复）

**常见坑** → 「飞书 / 开放平台」章节

---

## 阶段 5 · 上云部署（半天）

**目标**：公网可访问，进程常驻。

**动作**
1. 选机器：内部工具 2核2G 够用；**内存是硬约束**（PyTorch ≈ 1.5G，2G 机器别装）
2. 操作系统**统一 Ubuntu 22.04**（命令一致，别混 CentOS）
3. 先加 **swap**（2G 机器必备），再装依赖
4. 依赖用国内镜像：`-i https://pypi.tuna.tsinghua.edu.cn/simple`
5. 用 **systemd** 托管，不要 `nohup`：
   ```ini
   [Service]
   WorkingDirectory=/opt/app
   EnvironmentFile=-/opt/app/.env
   ExecStart=/opt/app/.venv/bin/python app.py
   Restart=always
   RestartSec=5
   ```
6. 安全组只放行必要端口（22 + 业务端口），**数据库端口永不开公网**

**产出**：`/etc/systemd/system/*.service` + 可访问的 URL

**门禁**
- [ ] `systemctl enable --now` 后能访问
- [ ] 服务器重启后自动恢复
- [ ] `free -h` 剩余内存 > 300M

**常见坑** → 「部署与打包」「网络与代理」「成本与计费」章节

---

## 阶段 6 · 数据迁移与校验（半天）

**目标**：数据完整搬过来，且能证明搬对了。

**动作**
1. 迁移前先**统计基线**：总条数、总金额、按类别分布
2. 迁移脚本必须**幂等**（`ON CONFLICT DO NOTHING/UPDATE`）
3. 迁移后**逐项对账**：
   ```
   源：18 条 / 440.10 元
   目标：7 条 / 323.20 元
   → 差 11 条，查明原因（重复文件），确认去重是正确行为
   ```
4. **对不上就停下来查**，不要假设"应该差不多"

**产出**：迁移脚本 + 对账记录

**门禁**
- [ ] 数量差异有明确解释（去重 / 过滤 / 失败）
- [ ] 金额合计能对上
- [ ] 有回滚方案（备份文件或快照）

**常见坑** → 「数据质量」章节

---

## 阶段 7 · 可观测性（2 小时）

**目标**：出问题 5 分钟内知道。

**动作**
1. **健康检查**三件套：Web 端点、进程状态、数据库连通
2. **去抖**：连续失败 2 次才告警（避免网络抖动误报）
3. **告警收敛**：只在状态刚变坏时推一次，持续故障不刷屏
4. 告警通道优先用已有 IM（本项目：用飞书应用机器人直接发，省一个 Webhook）
5. 提供**一键状态脚本**（`status.sh`），比让用户记命令友好

**产出**：`healthcheck.py` + systemd timer + `status.sh`

**门禁**
- [ ] 手工停服务 → 能收到告警（实测过）
- [ ] 恢复后不重复告警
- [ ] 一条命令能看全部状态

**模板**：`templates/healthcheck.py`、`templates/status.sh`

---

## 阶段 8 · 工程化（2~3 天，按需）

**目标**：改代码有安全网，换机器能重建。

**优先级**（性价比从高到低）
1. **监控告警**（阶段 7，已做）
2. **Docker 化**：`docker compose up -d` 一条命令重建
3. **单元测试**：先覆盖数据层 + 纯函数，别测 UI
4. **CI**：push 后自动 lint + test
5. **数据库迁移工具**（Alembic）：改表能回滚

**门禁**
- [ ] 换一台新机器，30 分钟内能拉起同款环境
- [ ] `pytest -q` 全绿
- [ ] 改表通过版本脚本而不是手敲 SQL

**详细步骤**：`skills/01~05` 那五份文档

---

## 阶段 9 · 安全与收尾（半天）

**动作**
1. 密码**哈希存储**（bcrypt/argon2），不要明文
2. 数据库**不开公网**，用 SSH 隧道：
   ```bash
   ssh -L 15432:127.0.0.1:5432 -N root@<IP>
   ```
3. `.env`、数据库文件、私钥：确认不在 git 里
4. 检查 git 历史里有没有塞过密钥（有就轮换密钥，不是删 commit）
5. 关掉不用的服务（本项目临时开的 API 服务用完后 `systemctl disable --now`）
6. 写清楚**已知限制**（诚实记录，比隐藏好）

**门禁**
- [ ] `git log -p | grep -i "api_key\|secret\|password"` 无命中
- [ ] 数据库端口公网不可达
- [ ] README 有「已知限制」章节

## 阶段推进的节奏建议

| 阶段 | 耗时占比 | 说明 |
|---|---|---|
| 0-1 需求+原型 | 15% | 快，别恋战 |
| 2-4 数据+AI+集成 | 40% | 核心价值所在 |
| 5-6 上云+迁移 | 20% | 最容易卡住 |
| 7 可观测 | 10% | 性价比最高 |
| 8 工程化 | 15% | 可延后，但别永远不做 |

---

## 每次卡住时的固定排查顺序

1. **分层定位**：网络？进程？配置？代码？
2. **看最底层的信号**（端口能不能连、banner 有没有回、DNS 通不通）
3. **看日志而不是猜**（`journalctl`、应用日志、服务端日志）
4. **做一个最小复现**（把问题从系统里剥离出来）
5. **查"最近改了什么"**（90% 的故障是最近一次变更引起）
6. 仍不通 → **换一条路径验证**（curl 换 python、SSH 换控制台 VNC）
